# Problem 3 — Linux pipeline agent disk pressure

## Cause and risk

The root filesystem is full (99 of 100 GB used), and the largest reported consumer is Docker at 76 GB under `/var/lib/docker`; the Azure DevOps agent workspace is another 12 GB. The summary alone does not say whether space is in build cache, images, containers, logs, or another Docker data directory. Deleting the wrong path can destroy a running job, cached build inputs, or data someone mistakenly stored in a container volume.

This VM is a build agent, not an application host. Its Docker artifacts and workspaces may be reproducible, but confirm that first and do not treat Docker volumes as disposable.

## Investigate before deleting

Run these read-only checks first:

```bash
df -h /
df -i /
findmnt /
sudo du -xhd1 /var/lib /opt/ado-agent /var/log 2>/dev/null | sort -h
sudo du -xhd1 /var/lib/docker /opt/ado-agent/_work 2>/dev/null | sort -h
sudo find /var/lib/docker /opt/ado-agent/_work -xdev -type f -size +1G -printf '%s %TY-%Tm-%Td %p\n' 2>/dev/null | sort -nr | head -50
sudo docker system df -v
sudo docker ps -a --size
sudo docker image ls --digests
sudo docker volume ls
sudo docker builder du
sudo journalctl --disk-usage
sudo lsof +L1
ps -ef | grep -E '[A]gent.Listener|[A]gent.Worker'
```

`df -i` checks inode exhaustion, while `lsof +L1` can reveal deleted-but-still-open files that continue consuming blocks; after identifying the owning process, release the space only through a controlled service restart. Docker's reports distinguish images, containers, volumes, and build cache. If Docker commands fail because the daemon is unavailable, inspect the daemon and logs rather than deleting `/var/lib/docker` directly:

```bash
sudo systemctl status docker
sudo journalctl -u docker --since "24 hours ago" --no-pager
sudo systemctl status
```

Before any cleanup:

- Check Azure DevOps for running jobs on this agent; identify the agent service and current job. Drain/disable the agent in its pool so no new job starts, then let active work finish or cancel it through Azure DevOps.
- Inspect the specific large directories and files, their owners, timestamps, and whether processes still use them. Check build, test, or deployment logs and local caches that may be needed to diagnose a failed release.
- Confirm images and build cache can be pulled or rebuilt, and that no container volume holds unique data. Ask the service owner before removing anything not clearly generated by the agent.
- Check the configured Docker data root and mounted filesystems. Do not assume everything under `/var/lib/docker` is safe to remove.

## Safe immediate recovery

1. **Stop accepting jobs.** Disable/drain the agent in Azure DevOps. Wait for running work to complete or cancel it safely. If service maintenance is required, use the agent's service script from its install directory (`sudo ./svc.sh stop`, if installed as a service); do not kill arbitrary processes.
2. **Remove aged unused build cache first.** Review `docker builder du`, then prune cache older than seven days:

   ```bash
   sudo docker builder prune --filter "until=168h"
   ```

   Review the prompt before confirming. This may make later builds slower, but it does not prune volumes or running containers.
3. **If space is still critically low, review unused images.** Confirm the agent can pull/rebuild them, then remove unused images interactively:

   ```bash
   sudo docker image prune -a
   ```

   This removes images not used by an existing container. Expect the next build to pull images again. Do not use `docker system prune --volumes` or manually remove Docker's data-root directories.
4. **Clean agent workspaces only when safe.** After confirming no job is using the workspace, use Azure DevOps agent maintenance/workspace-cleaning controls or remove only a confirmed stale job directory. Preserve diagnostic logs needed for the incident. Do not blindly delete all of `_work`, `_tool`, or agent configuration.
5. **Recheck and restore service.** Run `df -h /`, `df -i /`, and `docker system df -v`; confirm useful headroom, start the agent service if it was stopped, re-enable the agent, and run a small test build. Record what was removed and the space reclaimed.

If pruning disposable cache and images does not restore adequate headroom, stop cleanup and escalate: identify the specific consumer, then increase disk capacity or move Docker's data root to a properly sized dedicated filesystem using a documented migration. Do not improvise a live move of Docker data.

## Prevention

- Alert on both filesystem bytes and inodes (for example, warning at 75% and paging/pausing jobs at 85%) so cleanup occurs before builds fail. Monitor `/`, `/var/lib/docker`, and the agent work filesystem.
- Configure regular, bounded Docker build-cache pruning after confirming retention needs; use agent maintenance and pipeline workspace-cleaning settings for generated source/output between jobs. Keep the Azure DevOps diagnostic logs needed for troubleshooting.
- Set Docker container log rotation (for example `max-size` and `max-file` for the `json-file` logging driver) and journal retention limits so logs cannot grow without bound. Apply daemon logging changes through change control and restart Docker during a maintenance window.
- Use a dedicated filesystem or appropriately sized disk for Docker data and the agent workspace so build growth is visible and cannot unexpectedly consume the OS root filesystem. Keep an agreed free-space buffer based on the largest expected build.
- Keep this agent dedicated to builds; do not store application state, release artifacts that exist only locally, or persistent data in its containers/volumes.
